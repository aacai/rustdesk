# RustDesk 功能与技术架构说明

> 本文档基于源码梳理，聚焦项目结构与五个核心功能：**操作系统密码**、**文件传输**、**查看摄像头**、**终端**、**反转访问方向**。
> 注：`libs/hbb_common` 为独立 git 子模块（含 `fs`、`config`、`message_proto` 等核心实现），其源码不在本仓库内，涉及处仅按调用关系描述。

---

## 一、项目结构概览

| 目录 / 文件 | 作用 |
|---|---|
| `src/` | Rust 桌面主程序 |
| `src/server/` | 服务端能力：音频、剪贴板、输入、视频、网络、文件、终端 |
| `src/client/` | 控制端逻辑：连接、IO 循环、文件管理 UI 接口 |
| `src/platform/` | 平台专属实现（Windows / Linux / macOS），如 `gtk_sudo.rs` 提权 |
| `src/ui/` | 已废弃的 Sciter UI（`*.tis`），新 UI 在 `flutter/` |
| `src/rendezvous_mediator.rs` | 与 rustdesk-server 中继服务器通信、打洞、反转连接 |
| `flutter/` | 现行 Flutter UI（桌面 `flutter/lib/desktop/`、移动 `flutter/lib/mobile/`） |
| `libs/scrap/` | 屏幕捕获 |
| `libs/enigo/` | 跨平台输入模拟 |
| `libs/clipboard/` | 剪贴板同步 |
| `libs/hbb_common/` | 配置、protobuf 协议、共享工具（子模块） |
| `src/lang/*.rs` | 多语言翻译（`en.rs` 仅含与 key 不同的英文，其余按 `template.rs` 填充） |

连接模型：控制端（`client`）与被控端（`server`）先经 `rendezvous_mediator` 在中继服务器注册 ID，再建立加密（NaCl/box 密钥）p2p 或中继通道；所有功能（屏幕、文件、终端、摄像头）复用该通道，通过不同 `ConnType`/`FileAction` 消息区分。

## 二、核心功能详解

### 1. 操作系统密码（OS 密码认证与提权）

指**以操作系统账户凭据完成身份验证 / 提权**，区别于 RustDesk 自定义连接密码。

**关键文件与逻辑**
- `src/server/connection.rs`：登录握手核心。
  - `lr.password`：RustDesk 自定义密码（`password::has_valid_password()` 校验）。
  - `lr.os_login`（`OSLogin{username, password}`）：使用系统账户登录，主要用于**终端**场景（`should_use_terminal_os_login_scope`，仅 Windows/Linux）。
  - 失败提示常量 `TERMINAL_OS_LOGIN_FAILED_MSG = "Incorrect username or password."`（仅 Windows 终端）。
  - Linux headless：`try_start_desktop(os_login)` → `linux_desktop_manager::try_start_desktop(username, password)` 用系统凭据拉起桌面会话。
- `src/server/login_failure_check.rs`：防暴力破解。
  - `check_failure()` / `check_failure_with_scope()`、`FailureScope`（如 `TerminalOsLogin`、`Default`）。
  - 多次失败后临时封禁；终端 OS 登录还受 `try_acquire_os_credential_login_gate()` 并发闸门限制。
- `src/platform/gtk_sudo.rs`（Linux）：本地提权（如 polkit / pkexec）弹出系统密码框，以 root 权限执行需要特权的操作。

**流程**：控制端在 `LoginRequest` 中携带 `password`（RustDesk 密码）和/或 `os_login`（系统账户）；服务端校验二者，终端场景优先走 OS 凭据登录并受失败计数保护。

---

### 2. 文件传输（File Transfer）

在已建立的加密通道之上，以分块（block）流式传输，复用主连接而非新建端口。

**关键文件**
- `src/client/file_trait.rs`：`FileManager` trait，把 UI 动作封装为 `Data::*`（`read_remote_dir`、`send_files`、`create_dir`、`remove_file` 等）并发送 `FileAction` 协议消息。
- `src/client/io_loop.rs`：客户端 IO 主循环。
  - 维护 `read_jobs` / `write_jobs`（`fs::TransferJob`）；`Data::SendFiles` 立即传输，`Data::AddJob` 排队，`Data::ResumeJob` 断点续传。
  - timer 驱动 `fs::handle_read_jobs()` 周期性发送数据块；空任务时退化为 30s 心跳。
  - `FileResponse` 处理：`Digest` 比对大小/修改时间做同名覆盖决策（`Skip` / `OffsetBlk` 续传），`Block` 落盘，`Done` 修正 mtime。
  - `sync_jobs_status_to_local` 将进度持久化到 `PeerConfig.transfer` 以支持恢复。
- `src/server/connection.rs`：被控端。
  - `file_transfer: Option<(String, bool)>` 登录时由 `LoginRequest::FileTransfer` 设置。
  - `FileAction` 分支分发目录列举/增删改（`ReadDir`/`Create`/`Rename`/`Remove*` 等），多数委托给 `ConnectionManager`（`ipc::FS::*`）。
  - `Send`（对端读本端）/ `Receive`（本端写对端）；`FileResponse` 桥接 `WriteBlock`/`WriteDone`/`CheckDigest`。
- `libs/hbb_common/src/fs.rs`（子模块）：`TransferJob`、`JobType`、`new_send/new_receive/new_block/new_digest` 等真正构造与读写实现。

**协议数据流**
```
控制端                               被控端
Data::SendFiles ── FileAction ──▶  创建 read/write job
FileResponse(Block) ◀── 分块流 ──   本地读/写
FileResponse(Digest) ◀── 校验 ──    覆盖/续传决策
FileResponse(Done)   ◀── 完成 ──    修正时间戳
```
支持单文件、目录、拖拽；`Digest` 实现断点续传与同名文件确认（`SetConfirmOverrideFile` → `FileTransferSendConfirmRequest`）。

### 3. 查看摄像头（View Webcam）

将**摄像头**作为独立视频源推送，与屏幕捕获（`VideoSource::Monitor`）并列。

**关键文件与逻辑**
- `src/server/video_service.rs`：
  - `enum VideoSource { Monitor, Camera }`，`service_name_prefix()` 区分 `monitor` / `camera`，`get_service_name(source, idx)` 生成服务名，便于枚举多路摄像头。
  - `new(source, idx)` 为每种源启动独立 `GenericService` 视频服务。
- `src/client.rs`：
  - `ConnType::VIEW_CAMERA` 与 `FILE_TRANSFER` 平行；登录请求 `lr.set_view_camera(...)`。
  - `is_view_camera` 标志进入视频接收线程，复用 `video_handler.record_screen(start, id, display, is_view_camera)` 的录制路径。
- `src/client/io_loop.rs` / `src/flutter.rs`：客户端发起 `VIEW_CAMERA` 连接并对端请求摄像头视频流，渲染到 UI。

**流程**：控制端以 `VIEW_CAMERA` 连接类型发起会话 → 服务端 `video_service` 以 `VideoSource::Camera` 枚举并捕获摄像头帧 → 经视频服务推流 → 客户端解码显示。

---

### 4. 终端（Terminal）

服务端在受控机器上启动 shell 会话，双向转发输入/输出/错误流。

**关键文件**
- `src/server/terminal_service.rs`：终端会话服务，管理伪终端（PTY）或 shell 进程，转发 stdin/stdout/stderr。
- `src/server/terminal_helper.rs`：平台相关 shell 与权限辅助（进程启动、token 获取）。
- `src/server/connection.rs`：终端登录授权。
  - `self.terminal` 标志；终端场景走 `prepare_terminal_login_for_authorization()`。
  - `should_use_terminal_os_login_scope()`：Windows + 终端 + 提供 `os_login.username` 时，使用**系统凭据登录**（OS 账户），否则使用当前会话用户。
  - `TerminalAuthorizationMode::{OsLogin{scope}, SessionUser}`、`TerminalUserToken`。
  - OS 登录失败返回 `TERMINAL_OS_LOGIN_FAILED_MSG`，并计入 `FailureScope::TerminalOsLogin` 失败计数与并发闸门，防暴力破解。
  - `try_start_cm_ipc()`：授权后启动与 `ConnectionManager` 的 IPC。
- `src/server/login_failure_check.rs`：终端 OS 登录的失败计数与封禁。

**流程**：控制端请求终端 → 服务端判定授权模式（OS 凭据登录 / 会话用户）→ 校验（受 `login_failure_check` 保护）→ 启动 shell via `terminal_service` → 双向转发流。

---

### 5. 反转访问方向（Reverse Connection）

指**被控端主动连接控制端**，而非控制端主动连被控端。适用于被控端处于 NAT/防火墙后、控制端无法直接可达的场景。

**关键文件与逻辑**
- `src/rendezvous_mediator.rs`：
  - 被控端（`server`）与控制端（`client`）均向中继服务器注册自己的 ID。
  - `handle_request_relay(RequestRelay, server)`：处理中继/反向连接请求，协助两端经服务器建立信道。
  - `// key important here for punch hole to tell my gateway incoming peer is safe`：在 NAT 打洞时，用 key 标记“合法 incoming peer”，使被控端放行来自控制端的入站连接。
- 控制端通过中继服务器向被控端“请求回连”（reverse），被控端收到后主动发起连接，方向反转。
- 正常 `outgoing`：控制端 → 被控端；`reverse`/`incoming`：被控端 → 控制端，二者最终都收敛到同一加密通道，上层功能（屏幕/文件/终端/摄像头）逻辑不变。

**流程**
```
控制端 ──请求回连──▶ 中继服务器 ──通知──▶ 被控端
                                    ◀──主动连接── 控制端
                         （hole punch + 中继备用）建立加密通道
```

## 三、小结

| 功能 | 核心类型 / 枚举 | 服务端入口 | 控制端入口 |
|---|---|---|---|
| 操作系统密码 | `OSLogin`、`FailureScope` | `connection.rs` 登录校验 + `login_failure_check.rs` | `LoginRequest{ password, os_login }` |
| 文件传输 | `fs::TransferJob`、`FileAction`、`FileResponse` | `connection.rs` 文件分支 | `file_trait.rs` + `io_loop.rs` |
| 查看摄像头 | `VideoSource::Camera`、`ConnType::VIEW_CAMERA` | `video_service.rs` | `client.rs` 视频线程 |
| 终端 | `TerminalAuthorizationMode`、`terminal_service` | `connection.rs` + `terminal_service.rs` | `ConnType::TERMINAL` |
| 反转访问方向 | `RequestRelay`、`incoming peer` | `rendezvous_mediator.rs` | `rendezvous_mediator.rs` |
